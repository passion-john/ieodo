# 데이터 설계 v0.4 (2026-10-27 확정)

ieodo가 무엇을 어떤 표에 남기는지와 그 이유임. 표의 "역제안"은 처음 설계에 없던 칸을 구현하면서 더한 것이고, 칸마다 이유를 붙임.

## 원칙

1. **파일이 정본.** AI(Edit 도구)와 사람(Obsidian)은 파일을 직접 고침. DB는 마지막 사본과 수정 이력을 가짐. DB를 정본으로 두면 전용 편집기를 만들어야 하므로 택하지 않음.
2. **대화 쌍** = 사용자가 직접 친 말 + 모델의 마지막 답변. 하네스가 user 자리에 끼워 넣는 안내문(`<system-reminder>`, AGENTS.md 본문 등)과 모델의 중간 진행 멘트는 넣지 않음. 슬래시 명령은 이름만 남김. AI가 선택지를 내밀고 사용자가 고른 답은 대화 쌍이 아니라 8번 표에 둠.
3. **도구 호출·결과는 저장하지 않음.** 세션의 원본 기록 파일 경로만 가리킴. 파일 수정은 6번 표가 따로 남김.
4. **임베딩 없음.** 검색은 FTS5 글자 검색만 (50,000개에서 밀리초).
5. **저장 전 비밀값 가리기.** 사용자 말·답변·문서 본문·diff 모두.
6. **대화 쌍과 수정 이력은 추가만.** DB trigger로 수정·삭제를 막음.
7. git은 이 설계와 독립임. diff는 수집기가 만들며 git 이력을 읽지 않음.

| `size` | 파일 크기(바이트) | 역제안: `artifact`는 본문이 없으므로 바뀐 정도를 가늠할 단서가 해시와 크기뿐 |

**문서 범위 (2026-10-27 확정)**
- 프로젝트 루트 아래의 **`.md` 파일만** 문서로 봄. 빌드 폴더(`target/`, `Saved/`, `Intermediate/`, `node_modules/` 등)와 git이 무시하는 경로는 제외. 다른 글자 파일(`.txt` 등)은 문서로 보지 않음 ("대화와 md만 다루는 전문 도구"로 감).
- **전역 설정 문서는 포함.** 스캔이 아니라 정해진 경로 목록으로 둠: `~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md`, `~/.gemini/GEMINI.md`, `~/.claude/skills/*/SKILL.md`. 모든 프로젝트가 7번 표로 이 문서들을 가리킴.
- **산출물**(`artifact`): AI 세션이 만들거나 고친 파일 중 허용 확장자에 드는 것. 본문·diff 없이 경로·시각·해시·크기만 둠. 허용 목록은 아래 참고.

**종류와 판정 순서 (2026-10-27 확정)**: 이름 접미사 → 정해진 이름 → 경로 → `etc`. 파일 머리에 `kind:`가 적혀 있으면 그것을 우선함.

| 종류 | 판정 |
|---|---|
| `harness` | `CLAUDE.md`, `AGENTS.md`, `GEMINI.md` |
| `skill` | `*-skill.md`, `skills/*/SKILL.md` |
| `rule` | `*-rule.md` |
| `report` | `*-report.md` (보고서는 이 이름으로 통일함) |
| `record` | `STATUS.md`, `HISTORY.md`, `wiki/*.md` |
| `readme` | `README.md` |
| `artifact` | 허용 확장자의 이진·산출 파일 |
| `etc` | 위에 안 걸리는 `.md`. 넣지 않는 것이 아니라 `etc`로 넣음 |

**산출물 허용 확장자 (2026-10-27 확정, 허용 목록 방식·대소문자 무시)**

| 묶음 | 확장자 |
|---|---|
| 발표 | pptx, ppt, pptm, odp, key |
| 문서 | docx, doc, docm, odt, rtf, pages, hwp, hwpx |
| 표 | xlsx, xls, xlsm, ods, numbers |
| PDF | pdf |
| 이미지 | png, jpg, jpeg, gif, webp, svg, bmp, tiff, tif, heic |
| 영상·음성 | mp4, mov, webm, mp3, wav, m4a |
| 데이터 | json, csv, tsv, xml, yaml, yml |
| 웹 | html, htm |
| 글자 | txt |
| 묶음 | zip, tar, gz, 7z |

- 산출물은 **AI 세션이 만들거나 고친 파일만** 잡음. 첫 스냅샷에서는 기준점만 잡고 보내지 않으며, 이후 AI 답이 끝난 시점에 새로 생기거나 바뀐 것만 보냄(아래 "수집기 ②" 참고). 그래서 저장소에 원래 있던 `package.json` 같은 파일은 들어오지 않음.
- 컴파일 결과물·바이너리는 목록에 없으므로 들어오지 않음. 새 형식은 생길 때 추가함.
- key·pages·numbers는 폴더 형태로 저장될 수 있어 해시 계산을 따로 다룸(실제로 생기면).
- 글자 추출 저장은 나중에 필요하면 얹음.

### 6. 수정 이력 `document_change`

| 칸 | 뜻 | 출처 |
|---|---|---|
| `change_id` (키) | 순번 | — |
| `doc_id` | 5번 참조 | 역제안 (사용자 안은 문서명): 이름은 겹치고 바뀜 |
| `changed_at` | 수정일 | 사용자 |
| `change_kind` | 만듦 / 고침 / 이름 바꿈 / 지움 | 역제안: 이름 바꾸기·지우기는 글자 diff로 표현이 안 됨 |
| `session_id`, `turn_no` | 어느 세션의 몇 번째 대화에서 고쳤는지. **비울 수 있음** | 사용자 + 역제안: 사람이 Obsidian에서 직접 고친 경우 세션이 없음 |
| `diff` | unified diff 한 덩어리 | 사용자 ("수정 내용") |
| `body_hash_after` | 수정 후 본문 해시 | 역제안: diff를 순서대로 적용한 결과가 실제 파일과 같은지 검증 |

- unified diff는 `@@ -12,3 +12,4 @@` 머리에 옛·새 본문의 줄 번호가 적히고, 아래에 `-`(뺀 줄)·`+`(넣은 줄)이 순서대로 옴. 위치·뺀 것·넣은 것이 한 덩어리에 있으므로 두 칸으로 나누지 않음. 순서대로 적용하면 어느 시점의 본문도 복원됨.
- 만드는 방법: 수집기가 폴더 스냅샷을 비교해 바뀐 파일을 찾고 본문을 보내면, 서버가 이전 사본과 비교해 diff를 만듦. 누가 고쳤는지는 스냅샷을 찍은 시점으로 정함(아래 "수집기 ②" 참고).

### 8. 질문·답 `question_reply` (2026-10-27 추가)

AI가 선택지를 내밀고 사용자가 고른 결정. 하네스는 이 답을 글자가 아니라 태그로 감싼 JSON(Codex `<send_user_message_question_reply>`, Claude는 AskUserQuestion 도구 결과)으로 기록하므로, 태그를 떼는 규칙에 휩쓸려 사라지지 않게 따로 둠. 예전 설계의 `decision`(고른 것 + 버린 대안)이 하던 일을 자동으로 맡음.

| 칸 | 뜻 | 출처 |
|---|---|---|
| `session_id`, `turn_no` | AI가 질문을 던진 대화. 어떤 대화 뒤에 결정하게 했는지 | 사용자 |
| `question` | AI가 물은 글 | 사용자 |
| `answer` | 사용자가 고르거나 친 답 | 사용자 |
| `options` | AI가 내민 선택지 전부 | 역제안: 고른 것만 남기면 버린 대안이 사라짐 |
| `answered_at` | 답한 시각 | 역제안: 질문과 답 사이 시간이 보임 |
| `question_id` | 하네스가 준 질문 ID | 역제안: 재수집 때 중복 방지 |

- 질문이 한 번에 여러 개면 질문마다 한 줄.
- 답만 담긴 메시지는 태그를 떼면 비므로 대화 쌍(3번)은 만들지 않음. 답은 이 표에만 남음.
- Claude는 같은 턴의 도구 결과로, Codex는 다음 user 메시지로 답이 오지만, 둘 다 질문을 던진 턴에 묶음.

### 9. 추가 메시지 `turn_message`

답이 나오기 전에 사용자가 이어서 보낸 메시지. 대화 쌍의 `user_text`는 바꿀 수 없으므로 옆 표에 둠. 예: "테스트해줘"(대화 쌍) 뒤에 답 전에 보낸 "막히면 다른 모델을 불러".

| 칸 | 뜻 | 출처 |
|---|---|---|
| `session_id`, `turn_no` | 어느 대화 쌍에 붙는지 | 사용자 |
| `seq` | 그 대화 쌍의 몇 번째 추가 메시지인지 | 사용자 |
| `text` | 메시지 내용(비밀값 가린 뒤 저장) | 사용자 |
| `sent_at` | 보낸 시각 | 사용자 |

- 수정·삭제는 트리거로 막음. 같은 번호로 같은 내용을 다시 보내면 변화 없음, 다른 내용이면 항목 오류.
- `recent`는 대화 쌍의 `added_messages`로 보여 줌. `search`는 종류 `message`로 찾고, 범위 `turns`에 포함됨.

## 구현에서 굳힌 세부 규칙 (①, 2026-10-27)

설계 표에는 없지만 구현·감사 과정에서 정한 제약. 칸을 더한 것은 없음.

- 세션은 한 번 등록된 프로젝트·하네스를 바꿀 수 없음(시작 시각·원본 경로만 갱신). 대화 쌍이 세션 번호만 들고 있어, 바꾸면 기록이 통째로 다른 프로젝트로 딸려 감.
- 대화 쌍의 UPDATE는 "답이 비어 있던 행에 답을 채우는 것"만 허용. 답 없는 행의 다른 칸, 이미 답이 있는 행은 모두 거부. `INSERT OR REPLACE`도 거부됨.
- turn은 등록된 세션, turn_model·question_reply는 존재하는 turn, project_document는 존재하는 project가 있어야 기록됨.
- 문서 경로는 절대 경로이고 `.`·`..`·빈 조각·줄바꿈이 없는 한 가지 표기만 받음(같은 파일이 두 줄로 갈라지지 않게). 심볼릭 링크 해석은 수집기 몫.
- `artifact`는 글자 본문을 받지 않고, 이진 내용은 `artifact`만 받음. 본문 해시가 같아도 종류나 본문 유무가 바뀌면 변경으로 기록함.
- 검색은 FTS 후보 전체(상한 5,000)에 범위·프로젝트 필터를 건 뒤 limit으로 자름.
- diff 헤더와 오류 문구에 들어가는 경로도 비밀값 가리기를 거침.

**`record` 도구 (③ 일부, 2026-10-27)**
- 한 번 호출 = 한 세션의 묶음: `project{name, root_path}`·`session{session_id, harness, started_at, transcript_path}` + `turns[]`·`models[]`·`documents[]`·`replies[]`. 항목은 세션 번호를 들지 않고 봉투의 세션을 씀.
- 적용 순서: project → session → turns → models → documents → replies. project·session 등록이 실패하면(다른 프로젝트에 묶인 세션, 모르는 harness) 호출 전체가 오류이고 아무것도 적용하지 않음. 그 뒤로는 항목 하나의 실패를 `errors[]`에 `turns[2]`처럼 자리와 함께 남기고 나머지는 계속 적용함. JSON 형식부터 틀린 항목도 같은 방식.
- 응답은 수(`inserted`·`unchanged`)와 문서별 결과(`doc_id`, `change`)만 돌려주고 본문·질문·답은 되돌려 주지 않음. 되돌려 주는 경로와 인자 오류 문구도 가리기를 거침.
- 문서 항목: `op` = snapshot / rename / delete. snapshot은 `artifact`면 `hash`+`size`, 아니면 `body`(8 MiB 초과는 항목 오류, 옛 `record_event`와 같은 상한). `turn_no`가 있으면 그 세션의 그 대화에서 고친 것, 없으면 세션 밖 변경(사람이 고침). 문서는 항상 봉투의 프로젝트에 묶임(7번 표).
- 재전송(응답 유실 뒤 같은 묶음을 다시 보냄): 대화·모델·질문답·스냅샷은 no-op. 이미 지운 문서 지우기, 원본이 없고 대상이 있는 rename도 no-op. 단, "사라진 경로의 스냅샷 + 그 경로의 rename"이 한 묶음에 있으면 재전송 때 옛 경로 행이 하나 더 생김 — 수집기는 보내는 시점의 파일 상태로 스냅샷을 만들어 이 조합을 내지 않음(②의 규칙).
- rename 대상 경로가 지워진 문서의 것이면 그 행을 되살려(본문·해시·크기·종류를 옮김) 원본 행은 비우고, 양쪽 이력에 `rename`을 적음. 대상이 살아 있으면 오류. artifact는 해시가 같아도 크기가 다르면 변경으로 기록함.
- 수집기만 쓰는 도구지만 클라이언트 이름으로 막지는 않음(옛 `record_event`와 같음, 서버는 loopback 전용).
- 새 표는 `~/.ieodo/records.db`에 둠(옛 `groundlink.db`와 별도 파일). 옛 DB의 거취는 미정 4.

## 수집기 ② (2026-10-28 확정)

**대화 쌍**
- `turn_no`는 세션 안에서 사용자가 친 말의 순번. 수집기 로컬 DB에 세션별로 이어 셈.
- 사용자 말은 `UserPromptSubmit` hook 입력의 `prompt`(하네스가 안내문을 붙이기 전, 친 그대로)에서, 답은 `Stop` hook 입력의 `last_assistant_message`에서 가져옴. Claude Code·Codex 공식 hook 문서에 두 칸이 있음(2026-10-28 확인). 시각은 hook이 돈 시각.
- Enter 때 답 없이 보내고, 답이 끝나면 같은 쌍의 답을 채움(①의 "답 한 번 채우기").
- Esc로 끊으면 `Stop`이 돌지 않아 그 쌍은 답이 빈 채로 남음. 끊긴 중간 글은 답으로 넣지 않음(원본 기록 파일에 남음).
- 원본 기록 파일(JSONL)은 모델 이름·effort를 꺼낼 때와 메우기에만 읽음.
- Claude Code는 `Stop`을 답 줄을 기록 파일에 쓰기 직전에 부를 때가 있음(2026-10-29 실제 세션에서 확인). 그러면 그 대화의 모델 이름을 못 읽으므로, `Stop` 때 기록 파일에 답 줄이 아직 없으면 최대 1초 기다렸다가 읽음. 1초 안에 안 나타나면 다음 hook(다음 대화나 세션 종료) 때 채워짐. 기다리는 동안 수집기 DB를 잠그지 않음.
- 메우기(2026-10-28 확정): hook이 놓친 대화 쌍(세션 도중 hook 설치, hook 오류·시간 초과)은 다음 hook 때 원본 기록 파일에서 찾아 저장함. 목표가 "모든 대화 쌍을 남김"이므로 빈칸으로 두지 않음. 같은 쌍이 hook과 메우기 양쪽으로 와도 한 번만 저장됨.
- 메우기 때는 하네스가 사용자 말 뒤에 붙인 태그 덩어리(`<system-reminder>` 등, 3번 표 아래 목록)와 `[Request interrupted by user…]` 표시 줄을 잘라 냄. 목록은 수집기 코드 한 곳에 둠.

- 답하는 도중에 친 메시지는 Claude 기록 파일에 `queued_command` 줄로만 남으므로 그것도 사용자 말로 셈. Codex의 `<turn_aborted>`는 끊김으로 봄(그 대화는 답 없음). `!`로 실행한 명령의 입력·출력(`<bash-input>` 등)과 다른 세션이 보낸 메시지(`<agent-message>`)는 대화 쌍이 아님.
- 수집기는 한 번에 40MB까지만 보냄(서버 상한 50MB).

**문서 변경: 스냅샷 비교**
- AI의 도구 호출(Edit·Write)을 지켜보지 않고, hook이 돌 때마다 폴더 스냅샷(파일별 크기·수정 시각·해시)을 찍어 지난번과 비교함. 이유: 산출물은 대개 스크립트 실행(Bash)으로 만들어져 Edit·Write에 보이지 않고, 사람이 고친 것을 잡으려면 어차피 스냅샷 비교가 필요하므로 하나로 통일함.
- 크기·수정 시각이 같으면 해시를 계산하지 않음. 스냅샷은 수집기 로컬 DB에 둠.
- 대상: md 전부(git 저장소면 git이 무시하는 경로 제외, 아니면 제외 폴더 목록), 산출물은 허용 확장자 중 git이 바뀜·새 파일로 보는 것.
- 등록한 폴더가 git 저장소의 맨 위일 때만 git 목록을 씀. 더 큰 저장소(예: git으로 관리되는 홈 폴더)의 하위 폴더면 직접 훑음. 어느 쪽이든 안에 든 별도 git 저장소는 그 저장소의 git 목록(그 .gitignore)으로 읽음(저장소 여러 개를 담은 작업 폴더 때문).
- 귀속: AI 답이 끝난 시점(`Stop`·`SessionEnd`)에 찾은 변경은 그 세션의 그 대화 쌍, 사용자가 말을 칠 때(`UserPromptSubmit`·`SessionStart`) 찾은 변경은 세션 없음(사람이 고침).
- 한계: AI가 답하는 도중에 사람이 고친 파일은 AI 변경으로 기록됨.
- `PostToolUse` hook은 쓰지 않음.
- 첫 스캔에서 산출물은 해시하지 않고 크기·수정 시각만 기준으로 둠(큰 파일이 많아도 hook 시간 안에 끝나게). 대화 쌍은 스캔보다 먼저 저장함.
- 누가 고쳤는지(2026-10-28 고침): 문서 변경은 늘 프로젝트 기준으로 등록됨. 대화 번호는 확실할 때만 붙임 — 답이 끝난 순간 같은 프로젝트에서 일하는 중(사용자 말을 받고 아직 답이 안 끝남, 최대 2시간)인 다른 세션이 없을 때만. 둘 이상이 동시에 일하면 세션 칸을 비움. 폴더를 처음 훑을 때 찾은 것도 비움(원래 있던 것). 폴더는 세션끼리 같이 쓰고 파일에는 누가 썼는지가 남지 않으므로 추측이 틀릴 수 있는 경우엔 붙이지 않음.
- Codex 앱이 다음 말을 추천하려고 뒤에서 여는 세션("This is an app-generated request for a suggested next user message"로 시작)은 통째로 무시함.
- 이미 끝나 hook이 다시 오지 않는 세션은 `capture --transcript … --session-id … --project-dir …`로 기록 파일에서 다시 채움.
- 한계: 세션이 하나뿐일 때 사람이 동시에 고친 파일은 그 대화에 붙음. git이 새로 무시하게 된 파일은 지운 것으로 기록됨.

**Antigravity (2026-10-30 추가)**
- Antigravity hook(공식 문서 https://antigravity.google/docs/hooks, 2026-10-30 확인)은 대화 id·작업 폴더·기록 파일 경로·모델 이름만 주고 사용자 말과 답은 주지 않음. hook 입력에 이벤트 이름도 없어 설치할 때 명령에 `--event`로 붙임.
- 설치 위치는 프로젝트의 `.agents/hooks.json`. 이 파일은 hook 이름 → 이벤트 구조라 ieodo 몫은 `ieodo-continuity`(이름 변경 전 `groundlink-continuity`는 설치 때 지우고 바꿈) 이름 하나로 둠. 사용자가 끈 것(`enabled: false`)은 다시 설치해도 유지함.
- 대화 쌍: 기록 파일의 `USER_INPUT`(출처 `USER_EXPLICIT`) 줄에서 `<USER_REQUEST>` 안쪽을 사용자 말로, 다음 사용자 말 전의 마지막 `PLANNER_RESPONSE`(도구 호출 없는 답)를 답으로 씀. `<ADDITIONAL_METADATA>`·`<USER_SETTINGS_CHANGE>`는 잘라 냄. `Stop` 때 답을 닫음. 단, 이번 사용자 말 이후 띄운 하위 에이전트(`Created the following subagent` 줄의 `conversationId`)나 백그라운드 작업(`running as a background task with task id`) 중 끝났다는 알림(`SYSTEM_MESSAGE`의 `sender=`)이 아직 안 온 것이 있으면 닫지 않고 기다림. 앱이 그 알림으로 대화를 다시 깨우고 이어서 답하므로, 마지막 `Stop`의 답이 그 대화 쌍의 답이 됨(답은 한 번만 채울 수 있어 먼저 닫으면 중간 안내가 답으로 굳음). 기다림은 띄운 지 2시간까지이고, 새 사용자 말이 오면 이전 대화 쌍을 그때까지의 마지막 답으로 닫고 목록을 비움(이전 메시지가 띄워 둔 서버처럼 끝나지 않는 작업이 다음 답을 붙잡지 않게 함). `transcript.jsonl`은 긴 내용이 잘리므로 옆에 `transcript_full.jsonl`이 있으면 그것을 읽음.
- 모델: 기록 파일의 모델 변경 안내("`Model Selection` … to Gemini 4 Argon (High)")가 있으면 그 이름과 effort를, 없으면 `Stop` hook의 모델 이름을 그 대화에 붙임.
- 문서 귀속: `PreInvocation`은 모델을 부를 때마다 돎. 답의 첫 호출(그 대화가 작업 중으로 표시되지 않았을 때)에만 스캔해 그때까지의 변경을 사람 몫으로 두고 작업 중으로 표시함. 이후 호출은 바로 끝냄. 위의 기다리는 중에 알림으로 다시 깨어난 첫 호출은 사람이 아니라 그 대화 쌍 몫으로 스캔함(작업이 돌면서 쓴 파일).
- 앱 색인(`conversation_summaries.db`)에서 부모 대화가 있는 대화(하위 에이전트)는 통째로 무시함. 하위 에이전트의 `Stop`이 부모가 고치던 파일을 사람 몫으로 잡지 않게 하기 위함.
- 출력: `Stop`은 `decision`이 필수이고 `"continue"`면 에이전트가 멈추지 않으므로 늘 `{"decision":"stop"}`, 나머지는 `{}`를 냄. 경고는 표준 오류로만 냄.
- 실제 대화로 확인함(2026-10-30): 프로젝트 `.agents/hooks.json`이 따로 허용 없이 돎, 모델은 변경 안내에서 이름과 effort로 읽힘, 하위 에이전트에도 hook이 돌며 무시됨. 하위 에이전트를 기다리는 동작도 실제 대화로 확인함. 작업 시작은 도구 알림 자체(`Created At:` 다음 줄)만 셈. 같은 메시지에서 띄운 끝나지 않는 서버는 다음 사용자 말이 올 때까지 답을 붙잡음(사라지지는 않음).

## MCP 도구 (2026-10-27 확정: 4개)

| 도구 | 하는 일 | 누가 씀 |
|---|---|---|
| `record` | 수집기가 대화 쌍·문서 변경·질문답을 묶음으로 넣음 | 수집기만 |
| `search` | FTS 글자 검색. 대화·문서·질문답 중 범위를 고를 수 있음 | AI |
| `recent` | 프로젝트나 세션의 최근 대화 쌍 N개와 그 대화의 질문답, 그 대화가 고친 문서 | AI, 이어받기용 |
| `history` | 문서 하나의 수정 이력(시각, 세션·대화, diff) | AI |

- 입력(2026-10-28 구현): `search(query, scope=all|turns|documents|replies, project?, limit≤50, 기본 10)`, `recent(project? | session_id?, limit≤50, 기본 5)`, `history(path, limit≤200, 기본 20)`. 결과는 모두 새것부터. `search`의 대화·질문답 결과에는 그 대화에 답한 모델·effort가 붙음. `history`는 문서가 지워졌는지(`deleted`)도 알려 줌.
- 질문답만 모아 보는 도구는 두지 않음. `recent`·`search`로 대신하고 필요하면 그때 추가.
